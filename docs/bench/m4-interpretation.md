## 2. 诚实解读:为什么是这个结果

1. **冷启动是主因,不是语言缺陷**。gemma3:4b 对 Python 的掌握来自预训练语料(数以亿计的 Python 代码),对 Aether 只有系统提示里的 ~600 token 文档 + 4 个示例。任何新语言与「预训练母语」同台竞技都必然如此——这是本项目文档(设计对话)早已预判的「网络效应 vs 技术优势」问题,现在有了量化证据。
2. **失败模式 = 模型上限,而非诊断缺失**。逐轮 debug 显示:4b 把示例同构改写(fib/fact)没问题,但一旦需要**组合**未出现在示例中的结构(高阶函数 + 匿名函数 + 契约),就退化为幻觉(`(* n 2 - n)`、`[:pre ...]` 中缀混写)。修补回路的反馈始终是高质量结构化诊断(带错误码、span、修复建议),但没有能力执行建议。
3. **Token 效率已兑现**。同任务口径下,Aether 的 completion tokens 是 Python 的 **45%**(节省 55%)。考虑到系统提示是**一次性常数成本**(实际工具中跨任务摊薄),按「用户提示 + 生成」口径 Aether 节省 **63%**。这正是设计支柱 P5 的直接证据。
4. **静态验证的严格性有代价**。gcd 等任务的失败部分源于「契约可被 Z3 证伪即拒绝」——同样的代码在 Python 下能过测试,在 Aether 下因为契约矛盾被拦下。这是**设计意图**(宁可拒绝,不可放过),报告如实呈现。
