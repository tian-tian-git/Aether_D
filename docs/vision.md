# Aether 愿景与设计支柱

> 本文回答三个问题:为什么(AI 需要自己的语言)、是什么(设计支柱)、不做什么(务实边界)。
> 背景材料:仓库根目录 `AI跨语言设计.txt`(原始设计对话与调研)。

## 一、为什么:AI 写代码的现状与痛点

大模型本质是「下一个 token 的概率预测器」,而现有编程语言都是为**人类认知**优化的。这套错配带来三个硬伤:

1. **歧义税**:运算符优先级、隐式类型转换、缩进、作用域遮蔽……每一个隐式规则都是 AI 的幻觉源。AI 必须「脑补」语言背后的隐藏规则,首次编译通过率低。
2. **Token 税**:为人类可读性设计的语法冗长,AI 要为实现细节支付大量 token;已有项目(KARN 等)证明压缩 50%–76% 是可行的。
3. **验证缺口**:「逻辑不通但能跑」是 AI 代码最危险的失败模式。传统语言的测试是事后补救,而契约/形式化验证可以把正确性检查前置到生成回路里。

## 二、是什么:五大设计支柱

### P1 无歧义语法(AST 即语法)

- S 表达式风格:一切皆前缀调用,语法树与语义树重合,**没有**优先级表、没有隐式转换、没有遮蔽歧义。
- AI 只需「填空」而非「推理」,把认知负担从概率预测转移给确定性编译器。
- 附带收益:Token 压缩、结构化补丁(改节点而非改文本)天然成立。

### P2 契约驱动(Design by Contract)

- `pre`(前置)/ `post`(后置)/ `invariant`(不变量)是一等语法。
- 双层验证:运行时检查(兜底)+ Z3 SMT 静态验证(数值/数组域,能在编译期拒绝越界类缺陷)。
- 目标:AI 写「意图 + 边界」,编译器负责证明;错误变成「第 N 号节点违反第 M 号契约」的结构化报告。

### P3 默认不可变 + 显式效果

- 值语义、纯函数默认;副作用(IO、状态)必须显式声明。
- 目标:消灭未定义行为与隐式全局状态——AI 不需要「脑补」代码之外的隐藏规则,可模块化推理。
- 说明:「状态流 / 时空 GC」等激进构想属于远期实验方向,不在 v0.1 承诺范围(见 architecture.md 数据模型一节)。

### P4 同像性(Homoiconicity)

- 代码即数据:AST 可直接被语言自身读取、构造、替换。
- 支撑「写代码 → 运行 → 分析结果 → 修补节点」的闭环,是静态蒸馏与自举的语法基础。

### P5 AI 优先的工具链

- 结构化诊断:节点 ID + 源位置 + 错误码 + 修复建议,可直接喂回 LLM 形成生成—验证—修补闭环(M4)。
- Token 指标、一次通过率是项目的一等公民指标,与执行性能并列。

## 三、不做什么(务实边界)

| 不做 | 理由 |
| :--- | :--- |
| 推翻冯·诺依曼硬件 / 自研芯片 | 物理债现实:我们的定位是「AI 与现有硬件之间的语义胶水层」。 |
| 与 Python / C++ 全面竞争 | 生态网络效应不可战胜;Aether 是补充者,不是替代者。 |
| 追求人类可读性 | 人类审查走「反渲染器」通道(远期),语言本体服务 AI。 |
| 一步到位 MLIR / LLVM | 先树遍历解释器锁定语义(正确性优先),性能后端在 M5 按 ADR 选型。 |
| 语法糖 / 隐式魔法 | 与 P1/P3 矛盾;一切隐式规则都是 AI 的幻觉源。 |

## 四、与既有项目的差异化

现有 AI 语言项目已形成流派(KARN/Pear = Token 效率派,Zero = 程序表示派,IF-Lang/Prajna = 意图/契约派,Mapanare = 全栈原生派,NanoLang/Synoema = 形式验证派)。**Aether 的切入点是「契约验证 × AI 生成回路 × 渐进性能」的交集**:

- 契约不止是注释,而是贯穿解析、类型、验证、诊断、生成回路的**一等结构**;
- 诊断模型从第一天就按「可喂回 LLM」设计;
- 性能走渐进路线(解释器 → 选型后端),每个阶段都有可运行的交付物。

## 五、成功判据

- **MVP 成功(M2–M4)**:AI 生成的 Aether 代码可解析、可验证、可执行;在基准任务集上,「一次编译通过率」与「token 消耗」相比 Python 基线有**可量化**的改善。
- **中期成功(M5–M6)**:性能后端基准与 CPython 同量级或更优;自举 demo(用 Aether 写 Aether 工具)可复现。
- **远期愿景**:意图市场(经过验证的逻辑拓扑片段库)、硬件适配——列入路线图但不排期。
